# StrideWeave Invariant Registry

This registry records cross-cutting constraints that must shape code before it is
written. Read it while planning a change, not only after implementation. Ordinary
feature behavior belongs in `llms.md` and its focused tests; this document covers
rules that apply across modules, backends, or future implementations.

## How to Use This Registry

Before changing code:

1. Identify the affected invariant IDs below.
2. Preserve their canonical implementation choices in the design.
3. Run every listed enforcement mechanism relevant to the change.
4. Update this registry in the same change when adding, removing, or materially
   changing a cross-cutting invariant.

When an existing invariant is decomposed, its first independent rule retains the
base ID and later rules use lowercase suffixes (for example, `SW002`, `SW002a`,
and `SW002b`). This preserves established citations, keeps related rules visibly
grouped, and avoids renumbering unrelated invariants.

Enforcement labels mean:

- **AST** — enforced by `tools/lint_invariants.py`.
- **Ruff** — enforced by the selected rules in `pyproject.toml`.
- **Test** — enforced behaviorally by the referenced tests.
- **Build** — enforced by compiler, formatter, type checker, or sanitizer jobs.
- **Review** — not reliably provable by current automation; authors and reviewers
  must inspect it explicitly.

The evidence column names stable files and test functions rather than line numbers,
which move frequently.

### AST Checker Operation

Run:

```bash
uv run python tools/lint_invariants.py
```

With no arguments it scans `src`, `tests`, and `examples` without importing the
package. It parses each file once, ignores virtual environments, caches, build output,
and recognized generated Python files, and emits deterministic
`path:line:column: SWxxx message` diagnostics.

An intentional exception must be attached to the exact affected line:

```python
tensor[[i, j]]  # strideweave-lint: ignore=SW001
```

Multiple named codes may be comma-separated. Do not use broad file-level suppression.
Exit status is `0` when clean, `1` when diagnostics are present, and `2` for invalid
input, unreadable files, or syntax errors.

RT012 treats `DType.Float64` as an accumulator-only descriptor. It is a
registered `SimpleDType` under `DType.Floating` so plans and capabilities can
name it, but no carrier accepts it as storage.

RT013 matches an accumulating plan exactly in both accumulator kind and
accumulator dtype. `Accumulation.FLOATING` does not prescribe traversal or
association order; floating reduction order is backend-defined. Typed execution
options are validated centrally, remain separate from positional and saved
autograd tensor inputs, and cross profiling and composite lowered execution
without bypassing the outer capability gate.

`Generic` and native `CPU` both advertise and execute the `Float32` and
`Float64` `FLOATING` accumulator shapes for `reduce_sum` and `matmul`. The CPU
bridge resolves the requested plan with the caller's typed execution options and
validates the complete plan correlation before allocation or GIL release, then
selects an operation-local typed accumulator kernel that widens only already
encoded binary32 terms and narrows once to the planned `Float32` output; an
accumulator dtype no kernel implements is refused rather than approximated by
the nearest floating kernel. Matmul retains that forward selection in its fresh
operation instance so backward contractions reuse it. No carrier gains `Float64`
storage. Evidence lives in `src/strideweave/carriers/generic/capabilities.py`,
`src/strideweave/carriers/generic/execution.py`,
`src/strideweave/carriers/cpu/capabilities.py`,
`src/strideweave/carriers/cpu/native/_cpu_policy.hpp`,
`src/strideweave/carriers/cpu/native/_cpu_accumulation.hpp`,
`src/strideweave/carriers/cpu/native/ops/reduce_sum.cpp`,
`src/strideweave/carriers/cpu/native/ops/matmul.cpp`, and the accumulator tests
in `tests/test_cpu_plan.py` and `tests/test_generic_reference.py`.

RT013 treats dependent-carrier finalization as a cooperative, single-threaded
construction step. The implementation calls
`_finalize_dependent_capabilities()` once, after installing its dependencies and
before the unfinished instance becomes reachable elsewhere. Concurrent
finalization and leaking a partially constructed instance are outside the
supported extension contract; the framework does not synchronize calls to the
extension-controlled generator. Snapshot publication remains failure-atomic,
and a later sequential finalization call is rejected.

## Registry Maintenance

Use the existing prefix for the relevant layer (`SW`, `PY`, `RT`, or `CPP`) and the
next unused number for a new invariant family. When decomposing an existing family,
retain its base ID on the first rule and use lowercase suffixes for the rest. An entry
must describe:

- the invariant in positive, implementation-guiding language;
- the canonical choice when multiple implementations are possible;
- every enforcement category currently providing coverage;
- stable evidence locations;
- any deliberately permitted exception.

Do not claim **Test** or **Build** enforcement unless a failing example would actually
make that check fail. Mark partially automated constraints as **Review** as well. When
removing an invariant, remove or revise its enforcement in the same change rather than
leaving a stale registry entry.
